# 学校向けバックエンドの正本案

Nyxisの構造を、学校の文書・役割・所属・許可操作に対応づけるためのCedarスキーマとポリシーの下書きです。スキーマに操作の効果を明示し、ポリシーを認可の正本とし、ハンドラは認可層だけを通して読み書きする構成を目指します。

架空学校の共通設定例は [`school-policy.example.json`](../src/school-policy.example.json) です。共有範囲の初期プリセット、文書証明の初期禁止語、学校向け点検項目を同じJSONに置き、各機能が必要な部分を参照します。これは共通の**初期設定例**であり、学校ごとの配布・署名・認証や改変防止、全製品への強制適用は未実装です。共通の検証コードは形式・版・項目・値・文字数を検査しますが、設定の発行元や妥当性は保証しません。証明画面では禁止語を編集でき、検証者が期待する条件の真正性を別途確認する必要があります。点検結果も自己申告です。

対象を文書に限定せず、生徒・教員・管理者・AIエージェントが扱う連絡、共有、アカウント、端末、データ分析、設備の運用を対象として設計します。実装済みの端末用コマンドは、共通の5項目について自己申告に基づく点検と設定案を生成します。利用者がJSONポリシーを書く必要はありません。

```sh
node scripts/school-audit.mjs guide
node scripts/school-audit.mjs draft
node scripts/school-audit.mjs check school-backend/observations.example.json
node scripts/school-audit.mjs inspect-path <保存先>
node scripts/school-audit.mjs review school-backend/observations.example.json <保存先>
node scripts/products-demo.mjs
```

`guide` は各項目の目的を表示し、確認済み・未対応・分からないを順番に尋ねます。`draft` は設定案と物理チェックリストをJSONで出力します。`check` は報告された値を判定し、未確認または不適合がある場合は終了コード2を返します。いずれも設定の適用や実環境の自動収集は行いません。点検結果は入力した人の自己申告であり、実際の設定や漏洩の不在を証明するものではありません。

`inspect-path` は指定したファイル・フォルダーの所有者とPOSIX権限を実際に読み取る別の点検です。現在のユーザーが所有し、グループとその他に権限がない場合に `basic-mode-ok`、それ以外は `review-needed` とし終了コード2を返します。シンボリックリンクは拒否します。ACL、親フォルダー、管理者や同一ユーザーの別プロセス、ネットワークストレージの実効権限、点検後の変更は確認せず、安全性の証明や５項目の自己申告の代替ではありません。設定は変更しません。

`review` は共通の５項目に対する自己申告と、指定した１箇所の権限の実測を一つの結果にまとめ、未確認・未対応の項目と次に確認する内容を出します。実測結果を自己申告の「確認済み」に書き換えることはありません。対応事項がある場合は終了コード2です。対応事項がなくてもACLなどの未検査事項は残ります。

`products-demo.mjs` は架空データを使い、Writeの文書作成、Gateの加工、Proveの合計証明をブラウザなしで実行します。3製品の書き出し判定には同じ `sumi-egress-v1` の認可ルールを使い、未確認の書き出しを拒否します。学校向け5項目の点検は別の共通モデルであり、現時点ではこの認可ルールに結び付いていません。デモは実データの保存や配布を行いません。


架空の連絡文を使う端末デモは `node scripts/agent-loopback-demo.mjs` で自動実行できます。確認前は通信を拒否し、模擬承認後は共通設定語とメールを加工してから端末内の架空HTTPサービスに送ります。サービスは固定応答を返すテスト用で、LLMではありません。ポート `127.0.0.1:11434` が使用中の場合は既存サービスに接続せず中止します。

`src/agent-document.js` は、エージェントへ渡す前に共通JSONの文書証明用禁止語と利用者の追加語を合わせ、加工版を作ります。確認前は読み取りを拒否し、文書変更時には確認を失効します。`scripts/school-agent.mjs` の `summarize-ai` は確認・同意後にローカルOllamaへ加工版を渡す試作です。検出や指定語が不完全なら漏れるため、加工版の全文確認が必要です。OllamaやOS、他のアプリの動作は制御できません。送信テストには、架空応答を返す端末内HTTPサーバーとの実通信と、模擬通信を使用します。実モデルでの品質評価ではありません。

`src/agent-guard.js` は、確認した版の文書だけをエージェントへ渡すための実験用ゲートウェイです。文書管理側が版番号を指定して承認し、エージェントには `agent` 窓口だけを渡します。文書が変わると承認は失効します。判定記録はルール上の判定の整合性を再計算するためのもので、実際に操作が行われた証拠や、発行者を認証した署名ではありません。ゲートウェイの外で動くコードや他のアプリは制御できず、プロセス分離や実際のログインもありません。試作のエージェントはAIではなく、固定処理で文章の先頭を取り出します。

操作結果の `event` は、ルール上の判定と実際の実行結果を別々に示します。例えばルールが `allow` でも、文書が未確認なら実行結果は `denied` です。記録には操作・対象・版番号と理由を含め、文書本文は含めません。このイベントもメモリ上の情報で、改ざん耐性のある監査ログや第三者への証明ではありません。

エージェントの実行判定は `formal/Agent.lean` の小さなモデルと対応させ、実行に必要な５条件をLeanで検査します。32通りの真偽値の組合せについて実装の判定との一致も確認します。条件を作るコードやJavaScript全体、別プロセスの隔離まで証明したものではありません。詳細は `ASSURANCE.md` を参照してください。

現段階では**下書き**です。Cedarパーサによる検証、認証済み主体の取得、データベースの現在値の取得、ハンドラの効果制限、HTTP・ファイルストレージ・監査ログ・実行時の接続、Leanによるアプリケーション全体の認可安全性の検査は未実装です。実際の学校データを扱える状態ではありません。

Nyxisの構造をそのまま再現するには、これらを一体として実装し、信頼する前提と証明が対象とする範囲を確認する必要があります。ブラウザ上の自己申告や、ポリシー文字列を置いただけの状態を「検証済みのファイルサーバ」とは扱いません。
