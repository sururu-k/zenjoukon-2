# Leanモデルを可視化する

[保証の構造を見る](index.html)は、Sumiの16定理を3つの観点から選べる専用の入口です。既存の埋め込みレポートから原文、行番号、直接の依存先、公理を表示します。外部CDN・fetchを使わずローカルファイルでも動作します。URLのハッシュで定理を共有できます。図はモデルの説明であり、Leanをブラウザで実行するものではありません。


お預かりした Lean4SemanticBench のビューアを使い、Sumi の２つの Lean モデルを別々に表示します。データは各モデルのソースをコピーし、Lean 4.34.1 でビルドして生成したスナップショットです。ブラウザで開いて宣言を選ぶと、その定義や依存先、参照先を確認できます。

- [認可・情報流モデル](policy/index.html)：初期表示は `Sumi.trace_plaintext_noninterference` です。
- [エージェント判定モデル](agent/index.html)：左の一覧から `execute_requires_*` を選ぶと、各条件に関する定理を表示できます。

グラフは**Leanの小さなモデルの宣言と依存関係**を表示します。JavaScript、ブラウザ、OSを含む全システムの安全性や、情報漏洩全体の不在を証明するものではありません。文書のゼロ知識証明のNoir回路は対象ではありません。

## 検査結果と限界

Leanのビルドは両方成功しました。Lean4SemanticBenchのレポート検査は、エージェント側が全項目通過、認可側は２項目で不合格です。認可側では自動生成された `splitter` ２件の位置情報がなく、対象188宣言のうち原文を表示できるのは173件でした。グラフと一部の原文は表示できますが、**全宣言の原文・位置が揃っていると見なせません**。欠落15件を確認したところ、２件は `match` の `splitter`、残り13件は列挙型などから生成された `ctorElimType`・`ofNat`・`ofNat_ctorIdx` です。応募資料で対象としている手書きの認可・情報流の11定理とエージェントの５定理については、レポートの原文と行番号を元ファイルと照合し、すべて一致しました。詳細は各フォルダーの `check.log` を参照してください。ツールのチェックは、Leanの定理の正しさや実装との一致を新たに証明するものではありません。

ビューアは指定バージョンの p5.js と Tailwind を外部CDNから読み込みます。閲覧時にネットワーク接続が必要で、CDNにはアクセス元が見えます。入力文書を扱う画面ではありません。ブラウザから直接ローカルファイルを開いても動作します。

## 来歴と更新

元ツールはユーザー提供の `Lean4SemanticBench-main.zip`（SHA-256 `c7fa58186b4f3999952eea9253965a9a3be5137dbc997d208c3a986f7b1dfc3c`）。解析器と操作スクリプトは [vendor/Lean4SemanticBench](../../vendor/Lean4SemanticBench/README.md) に同梱し、[MITライセンス](LICENSE)を保持しています。元ツールのGitHub Actions設定は同梱していません。各 `report.meta.json` は一時Lakeプロジェクトで生成したためGitコミットIDを持たず、対象の実ファイルのハッシュは [manifest.json](manifest.json) に別途記録しています。複製した２モジュールには同名の `main` があるため、同時ロードせず別々に解析しました。

`npm run build` は元モデルとレポートの整合性を確認してから、可視化を `dist/lean/` に配置します。`npm run dev` でも保証範囲画面から開けます。`node scripts/check-lean-visualization.mjs`（`sumi` ディレクトリで実行）は、元モデルと、レポート・埋め込みデータのハッシュに加え、対象16定理の原文と行番号が元ファイルと一致するか確認します。モデルが変わった場合は同梱ツールでそれぞれ再生成し、チェック結果とハッシュを更新してください。操作方法は[ツールの説明](../../vendor/Lean4SemanticBench/Commands/Scripts/README.md)を参照してください。ハッシュは真正性の署名ではありません。
