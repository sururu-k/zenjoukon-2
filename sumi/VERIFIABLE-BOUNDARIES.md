# 検証できる境界を共通の部品にする

Sumiの文書証明、ツール結果の検証、実行権限の制御を、企業や学校の用途から呼び出せる下位レイヤへ発展させる。外部から得たデータやAIの提案をそのまま信頼せず、用途ごとに必要な条件を確認してから次の処理へ渡す。

## 秘匿したソフトウェア部品表の検証

部品表を外へ渡さず、確定した部品表に対する特定の依存関係を証明する。例えば製品Aから部品Dへの経路がある場合、経路中の部品を隠したまま、登録済みの依存関係集合にその経路が含まれることを証明する。

文書中の指定語の不在証明と同じく、非公開の入力をコミットし、公開条件に対する性質を示す。ただし、依存グラフの到達可能性は文字列検索ではない。経路の各辺と接続を検証する回路が必要になる。特に「経路がない」ことは経路の存在を示す証明より難しく、単一のMerkle非包含証明だけでは一般のグラフに適用できない。まずは固定長の経路存在証明を検討し、不在証明は別の課題として扱う。

証明対象は、あくまでコミットされた部品表である。網羅性、ビルド成果物との対応、スキャン時期、CVEの適用判定は別途確認が必要であり、証明だけで現実のシステムに脆弱性がないとは言えない。

## エージェントの実行ポリシー

所有者が設定したポリシーへの適合を、エージェントが提案した操作の実行前に検証する。秘密のポリシーを使う場合は、登録済みコミットメントに対応するポリシーを知っており、操作がその条件を満たすことをZKで示す構成を目指す。

証明は少なくとも対象システム、操作、対象、引数、期限、使い捨て番号に結び付ける。一定期間の支出上限には、現在の利用額と更新を原子的に扱う状態管理も必要になる。操作経路そのものが検証を必須にしなければ、ゲートを迂回できる。

現在の `src/secure/capability-gate.js` は、独立した署名の組と公開された条件を検証する試作である。ZKポリシー、ウォレットやOSの強制境界、再起動をまたぐ再利用防止は実装していない。また、指定語の不在だけでは、任意の個人情報を含まないことは証明できない。

## 検証可能なツール結果

ツール呼び出し、依頼先、依頼ID、検証対象の結果、証明を結び付け、クライアントが自分で検証した結果だけを後続処理へ渡す。検証鍵や信頼する署名者は、応答の送り手とは別に設定する。

現在の `src/secure/verified-sum-bridge.js` と `src/secure/verified-tool-gateway.js` は、コミット済みの値の合計証明と署名を検証するローカルなアダプターである。呼び出しの目的・ID・宛先を証明と署名に結び付け、同じ検証セッション内での再利用を防ぐ。`src/secure/agent-verified-tool.js` は、確認済みの対象と最低件数の条件を追加し、検証された結果だけをエージェントに返す。

この証明は、元データが真実であることや、一般の任意プログラムが正しく動いたことを示さない。現在のアダプターはMCP標準への準拠実装でもなく、TEEの遠隔証明でもない。検証時間は方式、証明、端末で異なるため、一定のミリ秒数を保証しない。

## 組み合わせる際の条件

1. 何を非公開にし、何を公開するかを決める。公開値やアクセス時刻による漏洩も残る。
2. 入力データやポリシーの正本を、誰がどの時点で保証するかを決める。
3. 証明、検証鍵、実行対象、使い捨て番号を結び付ける。
4. 検証成功後の実行を、別経路から迂回できないようにする。
5. 証明できる性質と、現実世界や端末に残る信頼を利用者へ明示する。
