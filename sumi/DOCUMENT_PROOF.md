# 指定した禁止語を含まない文書の証明

学校の文書を提出するとき、原文を第三者に渡さず、合意した禁止語が原文に含まれないことを示す仕組みを目指します。検査対象は指定された文字列との完全一致です。個人情報一般の不在や、意味の同じ別表現まで検出できるという主張ではありません。

## 複数語の実験版

`noir/document_absence_v2` と `scripts/noir-document-v2.mjs` は、512バイト以内の文書と、各16バイト以内の禁止語１〜４語を扱う別形式です。文書の長さ・禁止語とその個数・文書コミットメントは公開されます。元の文書とランダム値は証明に含めません。v1とはコミットメント・証明・開封情報の形式が異なり、互換性はありません。

例えば `policy.json` に `{"forbidden":["山田","佐藤","電話番号","内部資料"]}` を保存し、Noir 1.0.0とBarretenberg 6.0.0の場所を環境変数 `SUMI_NARGO`、`SUMI_BB` に設定したうえで実行します。

```sh
node scripts/noir-document-v2.mjs prove example.txt policy.json proof-v2.json opening-v2.json
node scripts/noir-document-v2.mjs verify proof-v2.json expected-v2.json
node scripts/noir-document-v2.mjs open example.txt opening-v2.json expected-v2.json
```

`opening-v2.json` は非公開です。検証者が別経路で確認する `expected-v2.json` は `documentLength`（UTF-8バイト数）、`forbidden`（順序を含む配列）、`commitment`（64文字の16進数）を持ちます。証明に添付された条件を無確認で受け入れてはいけません。検証鍵は検証者の手元の回路から生成しますが、その回路とツールの真正性の確認は別途必要です。

`node scripts/noir-document-v2-demo.mjs` は架空文書で４語の証明を生成・検証し、禁止語の混入・末尾での一致・コミットメントの改変を試します。`node --test tests/noir-document-v2-integration.test.mjs` は利用者向けコマンドも試します。両方とも `SUMI_NARGO` と `SUMI_BB` が必要です。１端末での１回の測定では、４語の回路の証明生成に約3.5秒かかりました。環境により変わります。

文字列はバイトの完全一致で、表記ゆれ・Unicode正規化・PDF解析・画像中の文字には対応していません。短い文書の実験であり、回路や暗号プロトコルは外部監査を受けていません。実際の学校データでの安全性を示すものではありません。

## ゼロ知識証明の実験

`noir/document_absence` に、別形式の小さな証明回路を追加しました。架空の文書（UTF-8で128バイト以内）に、公開された１つの禁止語（同８バイト以内）が完全一致で含まれないことを対象にします。文書とランダム値は非公開入力、文書のバイト数・禁止語・禁止語の長さ・文書コミットメントは公開入力です。公開された文書の長さや禁止語は隠れません。

Noir `nargo` 1.0.0 と Barretenberg `bb` 6.0.0 を用意し、`sumi` フォルダーで以下を実行すると、架空の文書について証明を生成し、公開値を照合して別コマンドで検証します。禁止語を含む文書と、公開コミットメントの改変が拒否されることも確かめます。

```sh
SUMI_NARGO=/path/to/nargo SUMI_BB=/path/to/bb node scripts/noir-document-demo.mjs
```

証明入力と生成物は一時フォルダーで作り、終了後に削除します。デモは今回の実行時に生成した検証鍵を使います。実用の第三者検証には、回路と検証鍵の信頼できる配布、検証者が期待する禁止語・文書コミットメントの照合、提出文書との対応が必要です。回路やプロトコルは外部監査を受けていません。[Noir公式の証明・検証手順](https://noir-lang.org/docs/getting_started_manually)も参照してください。

## 自分の文書で試す

実験用の短いテキストファイルを用意し、次のように証明と開封情報を別々のファイルへ出力できます。環境変数には上記と同じバージョンの実行ファイルを指定します。出力先は新しいファイルを指定してください。

```sh
node scripts/noir-document.mjs prove example.txt 山田 proof.json opening.json
```

`proof.json` には証明と、公開される文書長・禁止語・コミットメントが入ります。`opening.json` のランダム値は非公開に保ってください。２つのファイルのうち、開封情報の保存に成功した後で証明の保存が失敗した場合は、開封情報だけが残ります。

検証者は、期待する条件を信頼できる別経路で確認して、次の形式の `expected.json` を作ります。値は例です。証明ファイルの内容を無確認でコピーするだけでは、別の文書や禁止語の証明を見分けられません。

```json
{"documentLength": 24, "forbidden": "山田", "commitment": "64文字の16進数"}
```

```sh
node scripts/noir-document.mjs verify proof.json expected.json
```

検証コマンドは証明ファイル内の公開条件を期待条件と比較し、**手元の回路から検証鍵を生成**して証明を確認します。その回路ソースやツール自体の真正性は別途確保してください。相手に文書と開封情報を渡す場合は、以下で文書の長さとコミットメントを照合できます。開封情報を渡した相手には、別途入手した候補文書との一致を試され得ます。

```sh
node scripts/noir-document.mjs open example.txt opening.json expected.json
```

`SUMI_NARGO` と `SUMI_BB` を設定して `node --test tests/noir-document-integration.test.mjs` を実行すると、証明・別コマンドでの検証・開封、および条件や文書の差し替え拒否を試せます。

## 別のローカル検査

`src/secure/document-policy.js` は、文書と禁止語を端末内で照合し、一致がなければ文書のランダムな値付きハッシュとポリシーのハッシュを作ります。同じ文書でも毎回異なるランダム値を使います。文書とランダム値は非公開の証明入力として扱い、公開予定の部分には含めません。

**この処理単体は通常のローカル検査であり、ゼロ知識証明ではありません。** 上のNoir回路とはコミットメント形式も入力上限も異なり、接続していません。ハッシュだけから、第三者が禁止語の不在を検証することはできません。

現段階の入力は文書がUTF-8で4096バイト以内、禁止語は１〜８個、それぞれ１〜64バイトです。表記の正規化・大文字小文字の変換・意味の推測は行いません。例えば全角「Ａ」と半角「A」は別の文字です。禁止語のハッシュは候補が少ない場合、推測されることがあります。

## 次に必要な証明

証明回路の中で、非公開の文書・ランダム値から公開された文書コミットメントを再計算し、合意したポリシーのハッシュを照合し、指定語がどの位置にも一致しないことを検査します。検証者は、期待するポリシーと、対象の文書に対応するコミットメントを別途確かめる必要があります。証明と実際に提出された文書を結び付けなければ、別の文書についての証明を流用できます。

複数の禁止語、より長い文書、実際の提出ファイルとの対応、ポリシーと検証鍵の配布、異なる環境での再現を検討します。Unicode正規化や表記ゆれ、PDFのテキスト抽出、画像内の文字は現行の証明対象ではありません。

PDFや文字列に関するZKの先行例として [zkPDF](https://github.com/privacy-ethereum/zkpdf) があります。先行例との差は未調査であり、技術自体の新規性は主張しません。まず学校で必要な禁止語や提出手順を利用者と確かめる必要があります。
