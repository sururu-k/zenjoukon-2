# 秘匿集計の実装と前提

`privacy-lab.html` は、0〜180分・1人1回答の通学時間だけを入力する画面です。文章のマスキングと暗号計算は別の機能です。暗号集計を使っても、元の文章が安全になるわけではありません。

| 技術 | 実装と検証の範囲 |
| --- | --- |
| ZK | ristretto255上のPedersenコミットメントとFiat–Shamir Schnorr型証明。個別値を公開せず、コミットした値の合計を検証します。範囲証明、回答の真実性、匿名化の証明は含みません。独自のプロトコル実装は未監査です。 |
| MPC | 素数2^61−1上の2者加法秘密分散。提出ごとの合計を分け、担当者ごとに2組以上のシェアを加算してから統合集計を復元します。異なる学校による提出かどうかは認証しません。非共謀かつ手順を守る担当者を仮定します。悪意ある入力、担当者の共謀、学校別集計の差分からの推測は防ぎません。 |
| FHE系の暗号計算 | Microsoft SEAL / node-sealによるBFV準同型集計。多項式次数4096、20bit平文係数、SEALの128bitセキュリティ設定で、件数と合計を暗号文のまま加算します。計算関数は秘密鍵を受け取りません。最大1,000回答に制限します。秘密鍵に依存するノイズ予算は計算・公開しません。ブートストラップを使った無制限のFHE計算は未実装です。暗号文の真正性・計算正当性の証明は含みません。 |
| 差分プライバシー | 「60分以上か」のランダム化回答。確率3/4で正答、1/4で反転し、ε=ln(3)、δ=0の1回の公開を構成します。2bitの一様乱数で抽選し、浮動小数点のノイズ生成を避けています。人数が既知、1人1回答の置換隣接が前提です。同じ入力はセッション内で同じ結果を再利用します。再読み込み・別端末をまたぐ予算管理や、入力変更を含む繰り返し公開の予算制限はありません。 |
| TEE | 実行環境が未指定のため未実装・送信停止。対応実機、信頼する実行イメージの測定値、アテステーションの信頼起点が必要です。GitHub Pagesや通常のローカルLLMをTEEと表示しません。 |

## ファイルの交換

交換する結果は `workspace.saveDraft` を通り、確認したファイルをパスフレーズで暗号化して保存します。「結果ファイルを読み込む」で端末内に復号します。個別の数値、ZKのブラインド値、BFVの秘密鍵は交換ファイルに含めません。結果ファイルの形式は `sumi-crypto-artifact`、外側の暗号形式は既存の `sumi-encrypted-draft` です。

ZKでは証明ファイルを渡し、受取人が読み込んで「読み込んだ証明を検証」を実行します。公開される情報には件数・合計・コミットメントを含みます。合計値を検証するための証明であり、情報漏洩の不在を示す証明ではありません。

`src/secure/verified-sum-bridge.js` は、合計証明を通常の ECDSA 署名と組み合わせる別の試作です。用途・依頼ID・受取先を証明の公開コンテキストと署名対象の両方に結び付けます。検証者は期待する依頼と信頼公開鍵・必要署名数を証明とは別に用意し、依頼の一致、証明、署名をそれぞれ検査します。`npm run demo:bridge` で一般向けと学校向けの架空例を実行できます。既存の Prove 画面の交換形式とは別で、自動接続はされていません。

署名は対応する秘密鍵による署名を確認しますが、鍵の所有者の身元や、署名者が別人であることを示しません。証明もコミットした値の合計との関係だけを示し、入力の真実性・所属・各値の範囲を証明しません。`createSumVerifierSession` は検証者が依頼IDを生成し、同一セッション内では同時再送を含め一度だけ受け付けます。保存はメモリ内だけで、再起動・別端末・複数ノードをまたぐ再送防止はありません。状態を持たない `verifySignedSum` 単独では再送を拒否しません。信頼鍵の配布・失効、実際に提出されたデータとの対応、暗号ライブラリの正しさは別途必要です。公開される用途・依頼ID・受取先・件数・合計・コミットメント・証明・署名から得られる情報もあります。

MPCでは、各校がA・Bそれぞれのファイルを別々の担当者へ渡します。各担当者が受け取ったシェアを一括で読み込み、A宛てまたはB宛ての合算を実行します。取りまとめ担当者は両者の集計ファイルだけを読み込み、復元します。学校別のA・Bシェアを同じ担当者へ渡してはいけません。各校の回答数と集計IDはシェアのメタデータに含まれます。担当者が入力を改ざんしないこと、ファイルの送り先を正しく分けることが前提です。

別形式の二択アンケートでは、回答が０か１であることの証明、担当別の秘密分散集計、担当者ごとの ECDSA 署名を組み合わせる接続実験もあります。`npm run demo:survey-bridge` で実際のローカル HTTP 通信と検証を試せます。上記の `sumi-mpc-sum-v1` ファイル形式とは互換ではありません。両担当は同一プロセスであり、署名鍵の本人確認や担当者の非共謀、提出の網羅性を保証しません。詳細は [SURVEY.md](SURVEY.md) を参照してください。

端末版の `school-study.mjs` でも２組以上のファイルを、A・Bに分けて集計できます。同じ提出識別子の重複は拒否しますが、同じ学校が別の識別子で複数回提出することは検出できません。各シェアと担当者別の合算値は既存の暗号化形式で保存します。端末版では同じ担当者のファイルを共通パスフレーズで開く設計なので、パスフレーズの配布と担当者間の独立性は利用側が維持する必要があります。送信や相手の本人確認は行いません。手順は `TERMINAL.md` を参照してください。

BFVでは、元の端末で回答を暗号化してファイルを渡し、別の端末で読み込んで暗号文の集計を実行できます。同じ鍵で暗号化したファイルだけをまとめられます。集計結果のファイルを元のタブに戻して復号します。秘密鍵は永続保存しないため、元のタブを閉じると復号できなくなります。端末内で一連の処理を確認するボタンもあります。

別の開発用 API として `exportEncrypted` / `restoreFHEOwner` を用意した。パスフレーズで暗号化した秘密鍵ファイルと、別途確認した公開鍵 ID を使って復元できる。`npm run demo:fhe-key-backup` は架空データと一時ファイルで復元を試す。画面上の通常操作には接続していない。鍵のシリアライズ時には平文が JavaScript のメモリに一時的に存在し、確実な消去は保証できない。パスフレーズと鍵 ID の安全な保管・配布、バックアップ、失効や鍵の更新は利用者側に必要であり、暗号化保存は安全な復号サービスを意味しない。

DPでは、ランダム化した回答数から人数を推計します。真の回答数は結果に含めません。再公開のたびに保護予算は合成されます。この試作のメモリ内の再利用機構は、悪意ある利用者による再抽選を阻止するものではありません。

## 依存関係と検証

依存ライブラリはバージョンを固定し、`package-lock.json` を管理しています。基礎演算には [noble-curves](https://github.com/paulmillr/noble-curves)、[noble-hashes](https://github.com/paulmillr/noble-hashes)、[node-seal](https://github.com/s0l0ist/node-seal) / [Microsoft SEAL](https://github.com/microsoft/SEAL) を使用します。ライセンスはビルド結果の `licenses/` に同梱します。

`npm test` で改変したZK証明の拒否、MPCの正常な復元と重複・担当違いの拒否、ランダム化回答の全8条件の確率比、実際のBFV暗号文の加算・復号・違う鍵の拒否を検査します。Leanの11定理は認可と情報流のモデルを対象とし、これらの暗号プロトコルの安全性を証明したものではありません。
`npm run demo:verified-tool` は合計証明をローカル HTTP ツールへつなぐ例です。検証側がツール名と対象データ ID を依頼に結び付け、別途指定した署名鍵と証明を検証し、表示用の結果が証明と一致した場合のみ返します。依頼の再利用は同一プロセスの検証セッション内で拒否します。データ ID は公開され、その ID が実際のデータを表すこと、入力の真実性や範囲、ツール環境の真正性は証明しません。独自形式の接続例であり、MCP 準拠や暗号実装の監査を主張するものではありません。

検証付きツールをエージェントから使う接続例では、管理側が対象を許可し、１回の呼び出しを確認した後にのみツールを実行する。署名と証明の検証、公開対象の最小件数確認を通った合計だけをエージェントへ渡す。確認変更中の結果と確認の再利用は拒否する。最小件数はコミットメントの数であり、異なる人の数やデータの正しさを証明せず、差分攻撃を防ぐプライバシー予算でもない。管理側・通信処理をエージェントが迂回できないというアプリ内の前提であり、OS レベルの隔離は行わない。

ツール結果の署名付き記録は、対象 ID、依頼 ID、公開される合計・件数、証明と署名の要約を監査用の別鍵で署名する。第三者は別途受け取った元の証明、期待する依頼、証明用・監査用の信頼鍵を使い、両方の署名と証明を再検証できる。個々の入力は記録に含めない。ただし、これは署名者が結果を確認したという記録であり、エージェントが結果を利用した事実、入力の真実性、記録の網羅性や保存の耐改ざん性までは証明しない。

検証済みツール結果の監査ログは、署名付き記録と証明をハッシュで順番に連結する。検証者は、ログとは別に取得・保管した末尾ハッシュと件数、期待する依頼、信頼鍵を指定して検証する。既存のチェックポイントと比較する範囲で改変・並べ替え・削除を検出できる。公開される対象 ID・合計・件数・証明等はログにも含まれる。チェックポイントの真正性、保存先の耐障害性、記録されなかった操作や署名者の不正は保証しない。保存・共有は呼び出し側の責任であり、この実装は単一プロセスのメモリ内に記録する。

エージェントの接続例では、検証済みの公開候補を、結果を返す前に署名付き監査ログへ渡せる。記録処理が失敗した場合や、その間に承認が取り消された場合は、結果をエージェントへ返さない。監査先は管理側が設定する信頼された処理であり、実際に正しく保存したかをこの API 自体は保証しない。記録後に承認が取り消されれば、結果が渡らなくても候補の記録は残るため、記録は実際の公開を証明しない。監査先を設定しない既存の呼び出しには記録を要求しない。

監査ログはパスフレーズによる AES-GCM 暗号化ファイルとして保存し、復号後に署名・証明・ハッシュ連結を再検証して別インスタンスへ復元できる。正しい古いファイルへの差し替えも検出するため、期待するチェックポイントは暗号化ファイルとは別に保管する。期待する依頼と信頼鍵も別途必要であり、ファイル内から信頼設定を採用しない。固定長フレームの上限は約 1 MiB。パスフレーズの安全な配布、チェックポイントの耐久性や独立管理は利用者側で確保する必要がある。

検証付きツールの許可対象・最小件数・受取先には、管理者の独立した複数署名を付けられる。利用側は、署名ファイルとは別に受け取った信頼鍵・必要署名数と、期待する設定ハッシュを指定してからエージェントを起動する。証明用の信頼鍵は別に指定する。これは複数署名であり閾値署名ではない。正しい最新版のハッシュの配布、管理鍵の本人確認・失効、設定の変更通知は別途必要であり、設定ハッシュを固定するだけで自動的に最新版を判定するわけではない。

`npm run demo:randomized-tool` は、二択の架空データを 3/4 の確率でそのまま、1/4 の確率で反転し、そのランダム化された値の合計に署名とコミットメントの合計証明を付け、エージェントへ渡す実験である。人数が既知で、一人の二択回答を置き換える場合、正しく独立に乱数が生成され、他に生データを公開しなければ、１回の公開の理論上のパラメータは ε=ln(3)、δ=0。最初の抽選結果をデータ集合ごとにメモリ内で再利用する。

この試作では生データと乱数生成は一つの信頼されたツールプロセス内にあり、回答者の端末で乱数化する構成ではない。署名と合計証明は、ランダム化が正しく行われたことや、各値が二択から生成されたことを証明しない。別プロセス・再起動・重複データ集合・別経路での公開は予算に含まれず、実運用に必要な継続的な予算管理もない。生データを正確に集計する既存のツールやデモを同じデータに併用すると、この公開の保護は失われる。

正確な合計とランダム化した合計は、別々のツール ID を使い、その ID を依頼のハッシュと署名付き証明に結び付ける。エージェントに返す結果にもツール ID を含める。署名付き設定 v2 は利用するツール ID を指定でき、v1 は従来どおり正確な合計のみを指定する。これにより別方式の既存の証明をそのまま差し替えることは拒否できるが、署名者がランダム化を正しく行ったことは証明しない。

監査記録・暗号化復元も、正確な合計とランダム化合計の両方式を扱える。復元時は、ログに書かれた方式を鵜呑みにせず、各依頼について別途保持した期待方式を使う。期待方式を省略した従来の記録は正確な合計として検証する。ランダム化合計を記録できることは、乱数生成や予算管理の正しさを証明するものではない。

ランダム化集計のデモは、各データ集合の抽選済み合計と件数のみを暗号化ファイルに保存し、別途保持したファイルのハッシュを照合してから復元する。元の回答や個人ごとのランダム化回答はファイルに保存しない。同じファイルを別インスタンスで読み込めば同じ合計を再利用する。復元後の合計証明は、その保存済み合計になるように作った合成値への証明であり、元の各回答との対応や乱数生成を証明しない。別のスナップショットを作成・公開した場合や、重複する別集合、別システムからの公開は管理できない。チェックポイント・鍵・パスフレーズの独立管理と、追加公開の予算管理は利用者の責任となる。

署名付きツール設定 v3 は、ランダム化状態の暗号化ファイルのハッシュも固定する。専用のアプリ内接続は、設定の署名と別途指定した設定ハッシュを検証し、その設定が指定する状態だけを復元してからエージェントを起動する。証明用の署名鍵も、別途指定した信頼鍵と起動時に照合する。一般の外部通信アダプターでは v3 を受け付けず、固定値を無視した別状態への接続を防ぐ。

この固定は専用アダプターとその管理側を信頼する場合の保証で、証明書だけから乱数生成や使用されたファイルを暗号学的に証明するものではない。別のアプリや再署名した設定、重複データを含む別公開の予算管理は行わず、期待する設定ハッシュと鍵の配布・更新も別途必要である。

`npm run demo:fhe-attestation` は、BFV 暗号文の加算結果と復号結果を通常の複数署名へ接続する例である。検証者は別途受け取った入力暗号文と期待する依頼から暗号文加算を再実行し、署名付きの暗号文結果と一致するかを確認する。復号結果は信頼済み署名者による表明であり、正しい復号の ZK 証明や閾値復号ではない。悪意ある署名者が虚偽の平文合計を署名すれば、暗号文加算の再検証だけでは検出できない。人数・合計、公開鍵 ID、暗号文、依頼 ID は公開され、再実行防止・署名者の本人確認・鍵失効も別途必要である。

BFV 集計では、復号者が公開鍵パッケージを渡し、入力者は別途確認した鍵 ID と一致する公開鍵だけで暗号化できる。入力用 API は秘密鍵や復号機能を持たず、集計 API は暗号文を加算する。`npm run demo:fhe-attestation` は各入力者の暗号化器を別々に作ってから集計・署名検証まで動かすが、同じプロセスの模擬であり、組織・端末の独立運用は示していない。公開鍵 ID の真正性は配布時に別途確認する必要がある。

BFV 復号ゲートは、管理者が確認した暗号文の集合・対象・受取先・依頼 ID を一回の復号に結び付ける。確認前、別の暗号文、取消後、同じ依頼の再利用は拒否し、非同期集計中に取消された場合も復号直前に確認する。対象と受取先は事前に許可したものに限定し、少なくとも３件を要求する。この件数は独立した人の数を証明せず、複数回の合計の差分からの推測は防がない。管理側が生の復号器をエージェントに渡さず承認内容を確認するアプリ内の前提であり、OS 隔離、本人確認、再起動をまたぐ利用履歴やプライバシー予算は含まない。

BFV 入力の接続例では、各参加者が暗号文・参加者 ID・対象・受取先・集計回・暗号鍵 ID に署名する。管理側が別途指定した名簿と公開鍵で全参加者の署名を検証し、重複や欠落、別の集計回を拒否してから、確認済みの暗号文だけを復号ゲートに渡す。検証者が確認できるのは登録鍵による署名であり、鍵の所有者が別々の実在人物であることや入力の真実性、個々の暗号文の値域は保証しない。参加者 ID・件数・対象・集計回は秘匿されない。デモは同一プロセスで鍵を作る模擬である。

BFV 集計結果の一括検証は、参加者の入力署名、期待する集計回、復号依頼、暗号文の再加算、復号者の署名を別途指定された鍵と照らす。集計回 ID を復号依頼 ID と共通にし、同じ暗号文を別の集計回へ再署名したものを、既存の集計結果に結び付けない。集計回 ID の一意な発行や使用済み管理は呼び出し側の責任であり、この検証だけでリプレイは防げない。

BFV の集計結果は、期待する集計回・依頼・参加者・復号者の鍵を固定した検証セッションでも受け取れる。同じセッション内では、成功した結果の再利用と、検証中の同時実行を拒否する。検証に失敗した場合は正しい結果を再提出でき、検証中の取消しは成功結果を返さない。状態はメモリ内のみで、再起動・複数端末・別セッション間の再利用を防ぐものではない。外部処理が実際に一度だけ実行されたことも証明しない。

BFV 結果の一回限り検証について、４状態（受付可能・検証中・使用済み・取消済み）と４操作の Lean モデルを追加した。検証中の成功だけが受付を生むこと、成功後・取消後はいかなる操作列でも受付が生じないこと、任意の操作列で受付は高々１回であることなど８定理を検査する。実際の JavaScript の状態遷移関数とは全 16 通りを照合する。ただし Lean は暗号検証そのもの、非同期実行環境、プロセス分離や再起動をまたぐ使用済み管理を証明しない。

Node.js の検証例では、使用済み集計回を SQLite ファイルに記録する方法も用意した。同じ台帳を使う別プロセスは、検証成功後の原子的な一意登録により、同じ集計回を二度受け付けない。台帳は明示的に新規作成し、別途保持した台帳 ID を指定して開く。記録には集計回 ID と検証条件のハッシュを含む。この例は `node:sqlite` の使える Node.js 24 以降を前提とする。これは共有ストレージと SQLite のロック・耐久性を信頼するローカル実装であり、古いバックアップへの差し戻し、台帳の削除・改ざん、別の台帳や複数ホストを跨ぐ再利用は防げない。登録後にプロセスが停止した場合、外部処理が実際に完了したかどうかも保証しない。

# BFV の復号に関する重要な制約

Microsoft SEAL は、攻撃者が選んだ暗号文の復号結果や秘密鍵に依存する診断値を外部へ返すことが、秘密鍵の漏洩につながり得ると注意している。[SEAL のセキュリティ説明](https://github.com/microsoft/SEAL/security) 従来の試作は `invariantNoiseBudget` を呼び出して戻り値に含めていたため、この呼び出しと公開を削除した。

ただし、通常の復号結果にも注意が必要である。BFV の暗号文はそれ自体では真正性を保証せず、参加者の署名や件数制限だけでは、悪意ある参加者が作った暗号文の安全性を保証できない。現在の BFV 機能は架空データと信頼された参加者による研究用デモであり、信頼できない第三者からの暗号文を復号するサービスとしては使わない。ノイズ予算を呼び出さないため、任意の暗号文や計算について復号結果の正しさを確認したことにもならない。

BFV 鍵バックアップの実験では、ランダムな復旧用秘密を XOR で２つに分け、担当 A・B の異なるパスフレーズでそれぞれ暗号化する。`npm run demo:fhe-two-party-backup` で、両方のファイルとパスフレーズを使う架空の復旧を試せる。期待する公開鍵 ID とバックアップ ID は別途確認する。これは 2-of-2 の復旧用秘密分散であり、片方を失うと復旧できない。復元時には両シェアと BFV 秘密鍵が一つのプロセスに揃い、閾値復号・MPC 復号ではない。鍵とシェアの配布、端末の独立性、パスフレーズの安全性、JavaScript メモリからの確実な消去は保証しない。信頼できない暗号文の復号にも使わない。
